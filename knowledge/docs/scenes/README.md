# 景需求文档（scenes/）——每一景一页：该是什么、现在是什么、怎么验

> 2026-09-17 立。起因：翠嶂的 `projects/daguanyuan/scenes/cuizhang.json` 写着「group1 是进门第一眼正对的那一组」，
> `plan.json` 里正门轴线明明是 x=55，group1 在 x=8——两份数据各自成立，合在一起是错的，
> 没有一页纸把「门在哪、人从哪进、第一眼看什么、峰在哪、树在哪」放在一起，就没人能看出来。

## 这一层是什么

项目里关于一个景的信息散在四处，都是写给 agent 看的格式：

| 在哪 | 讲什么 | 不讲什么 |
|---|---|---|
| `knowledge/docs/qingshi/<景>.md` 考据稿 | **该是什么**（原文、旁证、可反算的数） | 现在摆成了什么 |
| `projects/daguanyuan/plan.json` 的 `basis` | **数字从哪来** | 整体构图 |
| `projects/daguanyuan/scenes/<景>.json` 的 `basis` | **每件落位的理由** | 件与件的关系 |
| `docs/superpowers/plans/` 单子 + `docs/reviews/` 验收 | **每一轮改了什么** | 累计到今天是什么 |

本目录补的是第五份：**需求文档**。一景一页，写「该是什么」与「现在是什么」的对照，
以及「怎么验」。**它是开单子的依据、也是验收的对照表。**算式不在这里，留在 basis 里。

## 每页固定六段

1. **一句话**：这一景在游线里承担什么（原文说的功能）。
2. **原文与定死项**：原文定死 / 参数集补 / 艺术选择，三栏分开，各附规则 id。
3. **视点、轴线、动线**：人从哪来、站在哪、眼高多少、第一眼看到什么、往哪走。数字全给世界坐标。
4. **构件清单与落位**：一张表，每行 = 构件 | 要求 | 现状 | 数据在哪 | 状态。
5. **植物与地面**：树、灌、藤、苔、地表材质；同样要求/现状对照。
6. **判据、机位、台账**：机位表（`tools/shot-list.mjs` 的 id）、可量的判据、门、未决与 bug、单子履历。

配一张 `<景>.svg` 现状平面（`node knowledge/docs/scenes/make-sketch.mjs`，只读数据不算几何，
每个点都能回溯到 plan / scenes / shot-list / HERO_TREES）。改了数据就重画。

## 规矩

- **开单子前先读这一页**；单子的「判据」段直接引用这里的 §6。
- **单子收工必须改这一页**的 §4/§5 现状列与 §6 台账，否则不算合回（`docs/superpowers/plans/STANDARD-ACTIONS.md` #15）。
- **验收人对着这一页验**：现状列写的每一个数都要能在世界里量到。
- 写「现在是什么」只许写量过的（机位图、普查脚本、manifest），不许写单子回报里的自述。
