## 3. 自然组件：值得做的四组改进

### 3.1 植物：分出树冠、叶团、枝隙，地被保留疏密

现有基础并不弱：有多种树形、根张、弯曲树干、树冠体积、外围叶片、逆光透叶和风动，不值得推倒重写。

[实景树冠与地被](/Users/huanghaibin/Workspace/games/daguanyuan/shots/review-20260910-codex/treeline.png) 中，近处冠层仍偏成块绿色表面，细叶纹理密；地被的许多高草簇具有接近的视觉权重。[竹子棚拍](/Users/huanghaibin/Workspace/games/daguanyuan/shots/review-20260910-codex/parts/bamboo_clump_three_quarter.png) 的竿节和整体形已成立，主要可以改善叶团的聚散。

建议：

1. **树冠先做负空间。** 保留现有实体内壳，让主要枝杈承接几个有大小差异的叶团，叶团之间留能透天的缝；削弱内壳表面的细密叶纹，用外围少量大叶簇打破轮廓。不靠加满 leaf card 获得“细节”。
2. **竹叶从每节均匀挂叶，变成少数枝扇。** 长竿仍有裸露段；部分短枝密、部分长枝疏；几支向院内探出，其余向外。风动保持竿缓、枝随、叶轻颤，幅度按离枝根距离增加。单丛已接近 5 万三角，先调分布和轮廓。
3. **种植分角色。** 建筑入口用框景植物，院角用遮挡植物，池边用低矮过渡，远处才是背景林带。每段先定视线空隙再散布；门洞正中的留白必须保留。
4. **地被分高度。** 低矮底层做连续色面，高草只落在少数团块；近路和屋脚的高草退后，落叶、苔和泥露出来。草地无需每平方米都长出同样醒目的大簇。
5. **mask 按米分辨率而非固定像素数。** 目前 280×226m 共用默认 256×288 mask，约 1.09×0.78m/texel；路边半米级边界会变得粗。按块烘焙，并以 0.2–0.3m/texel 作为近路试验值，块边保留采样边带。这个数是试验起点，不是史料或最终门槛。

来源：[植被构件](/Users/huanghaibin/Workspace/games/daguanyuan/builder/parts/zhiwu/vegetation.ts:318)、[种植 mask](/Users/huanghaibin/Workspace/games/daguanyuan/engine/scatter/poisson.ts:89)、[竹枝生成](/Users/huanghaibin/Workspace/games/daguanyuan/builder/parts/zhiwu/bamboo.ts:396)。

验收：在 2m、8m、25m 看同一植被组，分别读到枝叶、叶团、整体剪影；绕树观察不露大块卡片面；竹影与竿叶动向一致；缩成小图仍能分辨竹、阔叶树和地被。

### 3.2 水：先做“池与岸”，再考虑反射

[沁芳水面](/Users/huanghaibin/Workspace/games/daguanyuan/shots/review-20260910-codex/bridge_mid.png) 的细纹在大片水面上很抢眼，亭柱与水之间缺少倒影联系。当前深度输入错误是先要排除的原因；不能据此直接判断全部 shader 都需要重写。

建议分两步：

- **第一步不加 pass。** 修深度场后降低中高频法线的视觉权重，保留大块平静水面；近岸表达水下泥石、贴岸暗湿带和少量漂浮物。现有透明浅水、Fresnel、距离衰减可以沿用。
- **岸线和驳岸用同一曲线。** 目前 `shoreStones()` 从池的 bbox 椭圆沿 18 个角度搜索，再跳过部分点；适合试摆，难以支持凹岸、小港和长岸。沿实际湿干交界提取/采样岸线，按弧长布石，石头朝向取岸线切线，埋深取当地标高。桥口、台阶、低植被带显式留缺口。
- **第二步只做一个反射试验。** 在沁芳亭旁比较“无反射”与“低分辨率主景平面反射”。反射只包含亭、近岸树石等能改变空间读感的物体，并按可见性和相机变化更新；不用全场景 SSR 或动态全景探针。反射必须被水色、粗糙度和轻微扰动压住，保留绘本式水面。

当前 PMREM 环境图由天空独立场景生成，不包含亭、树或云，所以增大 `envMapIntensity` 不能获得它们的倒影。[环境烘焙](/Users/huanghaibin/Workspace/games/daguanyuan/engine/render/Atmosphere.ts:258)。

验收：岸石不漂、波纹不压过建筑，移动视角能保持亭脚与水面的联系；反射方案只有在画面改善且新增 GPU 开销可接受时保留。

### 3.3 山石：把“满身小坑”让位给石势、褶皱和洞

[独峰棚拍](/Users/huanghaibin/Workspace/games/daguanyuan/shots/review-20260910-codex/parts/taihu_peak_three_quarter.png) 已经有真实透孔，这是很好的基础。但大量近似大小的圆坑遍布表面，容易读成多孔泡沫；[假山组](/Users/huanghaibin/Workspace/games/daguanyuan/shots/review-20260910-codex/parts/taihu_mound_three_quarter.png) 多块石的竖立姿态接近，容易读成若干独峰并排。

建议：

- **大形：主峰、靠石、脚石分形。** 主峰允许较窄高，靠石横卧或斜撑，脚石压低并入地。只共享同一套石质，不共享同一种站姿。组内褶皱有大致连续走向，接缝靠局部错叠与苔遮住。
- **中形：少数贯通的槽与不规则洞。** 让洞成为轮廓事件，有大小、深浅与方向差异。孔洞朝游线的现有设计保留。
- **小形：减少均匀圆坑。** 当前 `taihuMaps()` 的 Worley 小坑同时影响 albedo 和强 normal；先把该项强度减半做 A/B，再观察是否需要改几何。湿色主要依据近水、下表面和凹处，避免整块随机发青。
- **不要先加网格。** 本次棚拍单峰约 26.2k 三角，假山组 116.8k。优先把预算花在外轮廓、洞口和玩家伸手可近的石面。

来源：[石材小坑](/Users/huanghaibin/Workspace/games/daguanyuan/builder/parts/materials.ts:281)、[石组构型](/Users/huanghaibin/Workspace/games/daguanyuan/builder/parts/shishan/taihu.ts:687)。

验收：中性棚拍与园中都能读到主次；关掉纹理仍有石势和透孔；人视高转过假山前后，确实形成遮挡与显露。不要只验“孔能打通射线”。

### 3.4 云：先改天空构图和明暗，体积云延后

现有 27 片云共用四种图集轮廓、单 draw call，工程性价比很好。实景里明显的问题是多个完整云朵像同等级图标排在天上，亮部较白、下缘有彩边。

- 先减少同时完整入镜的中型云：保留一两个主要云团，其余拉开尺度、重叠、位置和清晰度；地平线云更低对比，天顶给蓝天留空。
- 先隔离云材质、bloom、色差和景深做 A/B，确认彩边/发白来自哪里，不直接归咎于贴图。也不因云而改全场景曝光。
- 目前云在贴图里用固定方向烘焙明暗，又是朝相机的 billboard。若转向观察仍显纸片，可把烘焙的高度/法线数据保留下来，按世界太阳转入 billboard 局部方向做廉价照明，再考虑少数错深度云片。该方案只是下一档试验，不保证单法线图能产生真实体积。
- 固定天气的远云需核对新世界尺度下的视差和远裁面。天空穹顶已跟随相机，云层仍绕世界原点旋转；跨区移动数百米时，两者的空间策略应明确一致。

来源：[云的烘焙](/Users/huanghaibin/Workspace/games/daguanyuan/engine/render/Clouds.ts:175)、[云片与分布](/Users/huanghaibin/Workspace/games/daguanyuan/engine/render/Clouds.ts:357)。

验收：360° 转向后光向可信，轮廓无醒目彩边；站在正门和潇湘馆都不会看到突兀放大的云片或切边。只有这些做完仍不满意，才评估路线图 PX 的体积云。

### 4.2 最小扩展契约

先在“潇湘馆正房—月洞门—西廊”这一个区域验证，其他区域不一起迁。

| 数据 | 用处 |
|---|---|
| 稳定 id 与局部 transform | 改显示名称不会把锚点匹配改坏；院内整体旋转仍能一起移动 |
| 真实 footprint 与檐口 envelope | 台基、植物避让、邻屋净距分别用正确外形，避免把屋顶外包盒当可走地面 |
| ports：入口/廊端/桥端的位置、方向、标高、净宽 | 用明确接点连接，能够查高差、朝向和通行净宽 |
| 地基 pad：边界、标高、过渡坡带 | 保证整个建筑支承区域稳定，不只在中心采一个 ground height |
| 构件自己的平台与阻挡数据 | 几何改了，碰撞和导航随之变；composer 不再重写桥的三段尺寸 |
| 关键视点与目标、遮挡物 | 门洞对什么、转角前藏什么可以审查，沿用现有 PE 思路 |

顺序为：**推导尺寸与占地 → 确定地基/水沟/连接 → 生成几何与碰撞 → 避让散布 → 视点验证**。不要仅仅把“植树”挪到“起屋”后面；那样仍然留着两套 footprint。

线性构件共享“路线采样与接点”机制，但分别有自己的几何生成器：墙需要连续压顶、廊需要柱网与转角屋顶、桥需要连续桥面和岸端台阶。不能把同一套固定模块强行弯成所有东西。

这些字段可以先是区域内 TypeScript 数据，不以马上搬成全园 scenes JSON、建编辑器或做约束求解器为前提。符合 D-18/D-22 的阶段取舍。

### 4.3 布局试验的具体目标

- **潇湘馆：让门、竹、屋形成前中后三层。** 保持原文/真源确定的建筑锚点，先调整可裁量的院墙、竹丛、入口衔接。月洞门框住一段竹与屋角，入门转身再见正房，院内明确一条干燥可走的路。当前月洞门几乎直接框正房门，这也可以保留为备选，以同机位 A/B 选，不把“必须错位”当历史事实。
- **沁芳亭桥：曲折发生在路径的大方向上。** 保留少数有作用的转折和停步点，中间用较长平静桥段承接；接头不重复栏杆或在水中反复生台阶。转折服务“看什么”，不只是为了让模块拼满长度。
- **翠嶂出口到潇湘馆：用局部空间段落引路。** 夹道结束后保留开阔水面，在下一处转向用岸线、矮墙或植物团提示方向；不因路长就沿路平均摆亭、石、树。

验收采用三个高度层次：俯视查连通，人眼高度查景，近地面查支承与台阶。PE 的射线也必须升到 3D：对目标体积取多条射线，考虑门洞净空与遮挡高度；一个平面 polygon 挡住中心连线，不足以证明屋顶、亭角都被挡住。

建筑扩展还需注意：当前可见建筑仍由 `deriveBuilding()` 的 fashi 入口生成；qing/fayuan 模块的存在不等于已自动接入每个 tier。后续应把各参数集归一成几何消费的米制骨架，再接实景建筑，不能只改 plan 的 style 标签。[当前入口](/Users/huanghaibin/Workspace/games/daguanyuan/builder/parts/damu/building.ts:307)。

## 5. 细节预算：分块比继续堆面更急

七张 1600×900 截图报告 sceneStats 约 **3.78–5.00M 三角、71–199 calls**。这里三角数是阴影加主场景的提交量，不是唯一模型面数；PostFX 已专门保留了这套统计口径。它高于艺术圣经的 2.2M 目标，但低于 P1 Task 6/7 明确放宽到的约 7.9M 阶段上限，因此不能据此判当前 P1 超预算。

截图 harness 的滚动读数为约 1 FPS。后续独立探针确认使用 ANGLE Metal / Apple M4 Pro；但没有做稳定时长的交互帧时与 GPU 分项测量，所以不能把这一读数外推成所有机器上的帧率，或断言某一个 pass 就是全部瓶颈。

第二次独立运行的构建耗时约 42.8s：地形 24.7s、植被 8.8s、建筑山石 7.4s、水 1.5s、天空 0.4s。启动变慢主要落在世界生成，不是需要凭 bundle 警告猜测。

建议落实已有 P1 Task 7，而不是另起重构：

- 地形目前是一整张约 549k 三角的 mesh；建筑按材质跨区合并，部分 mesh 的 x/z 包围盒跨近 200m。按空间块再按材质合并，才能按可见区域剔除；别只追求 calls 小。
- 地形每顶点采一次高度，再为法线额外采四次。分块时共用带边带的高度格，缓存相邻采样，法线从格中求导；共享边界采样，避免裂缝。远处地形再降分辨率。解析高度与可行走网格的差异必须控制，不能只宣称用了同一个函数就等于表面精确重合。
- 把近景预算优先给石孔、竹枝、檐口；远处保持可辨认轮廓，不为看不见的微小凹凸交同等预算。
- 先测分块后的稳定帧时与 scene/frameStats，再决定是否承担反射或体积云的新 pass。

## 6. 随原排期使用的三个验收样板

1. **P1：环境坐标与分块收尾。** 继续 Task 7；额外核对水深/树丛/树碰撞/阴影是否已归到同一活动世界。验四区截图与稳定帧时。
2. **P3：一套岸边自然物样板。** 一块主石、一组竹/树、一段实际岸线和水。只用现有程序化管线，以同视角 A/B 选择形体、纹理密度和接地；反射作为可删的试验。
3. **P2/PE/P4：潇湘馆连接样板。** 数据、关系与区域建设分别随原阶段落地，用 ports、footprint、pad 贯通入口—月洞门—正房—廊，改一个开间后相关净空和植物避让能自动跟随；键盘完整走通并从三个视点审画面。

先不做：全园增加噪声/面数、同时铺满所有植物品类、全部区域改布局、全自动园林求解、完整体积云。当前最值得补的是空间关系与输入一致性；这些做好后再选一两处精雕，收益更容易看见和验证。
