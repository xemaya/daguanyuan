## 0. 原则

- **平面图驱动**:`projects/daguanyuan/plan.json` 是园子的真源。区域边界、路网、水系、景点、出处回目都在里面;
  装配器按区域读 `scenes/<区域>.json`,不再手写一张大表。
- **分而治之**:一个区域 = 一个可独立建设、独立验收(棚拍 + 区域截图 + 试玩)的单元 = 一个 agent 的并行任务。
- **原文最高,法式守底**:优先级栈见 ART_DIRECTION.md §1.5(原文 > 清式形制 > 法式结构 > 江南审美);大木作数字只从 `builder/derive/` 出,参数集按 tier 选;新建筑类型先补推导规则再出几何。
- **每一步可交付**:每加一区,游线延长一段,随时能上线试玩。

### 为什么 PQ 要拆两半

**你要优化的东西里,有一半正好是 WG 要重写的那几组 shader。** WG 方案列的高风险项是
地形材质、水、通用植被、竹——而「草」「水」「地面混合」「云」就在里面。
**先用 GLSL 把草和水调好再翻成 TSL,等于做两遍。**

| | 内容 | 与 WG 的关系 |
|---|---|---|
| **PQ 几何半**(先做) | 铺地构件、雕花(雀替/椽/格心/柱础)、灯、树种换血、花种类、草的**分布与斑块**、正门形制 | **不冲突**——TSL 迁移不动几何,现在做的将来不用重做 |
| **PQ 着色半**(WG 之后) | 草的**分层着色与露土**、水的**流动**、地面四档混合、体积云(PX) | **直接冲突**——这些就是 WG2 要转成节点材质的那几组 |

### P1 增补:构件级本体(2026-09-10 由同题论文调研引入)

现在 `knowledge/rules/` 只到**规则**粒度(举高怎么算),没到**构件**粒度(斗拱由哪些分件
构成、每件什么形状、怎么连接)。这一层空着,是我们几何看起来比同题工作"单薄"的直接原因
——对方的建筑构件图谱有 3505 个实体,我们的铺作是三个倒角箱体摞起来。见
`docs/kg-paper-borrowing.md` §3.1。

新增 `knowledge/rules/components.rules.json`,与规则表并列但语义不同:规则表回答"多大",
构件本体回答"由什么组成、怎么装"。字段:

- `id` `name` `category`(斗拱/梁架/柱额/屋面/小木/石作)
- `parts[]`:下级分件的 id 与数量(如 五踩斗拱 → 栌斗 1、华栱 2、令栱 1、耍头 1、撑头木 1…)
- `attachTo`:装在哪个父件的哪个位置(枋心/跳头/柱头/角部)
- `geometry`:形状族(斗/栱/昂/枋/替木/椽)与该族的形状参数名
- `dimensions`:引用规则表里给尺寸的那条 id,**不在这里重复数值**
- `source` `status`:同规则表,走同一道 `check:rules` 门

来源以 `knowledge/docs/qingshi/04-dougong.md`、`knowledge/docs/fashi/02-puzuo.md` 为主,
批评稿点名缺的(铺作三维叠层与里跳、替木、衬方头、转角列栱)一并补进 `missing.rules.json`。

**本体只存"是什么、怎么装",绝不存几何**。不许出现顶点、网格、贴图路径这类字段——
一旦存了,这套东西就从可执行的语法退化成一个巨大的古建资产库,而那正是我们最独特的
地方丢掉的时候。几何永远由 `builder/parts/` 按 `本体 + 规则 + spec` 现生成。

**先做斗拱一类跑通链路**,证明"本体 + 规则 → 真分件几何"成立,再铺开到梁架与小木。

### PQ-0 光与色的纪律（三处能量出来的错，不是审美差距）

**① 雾的密度是按 64×72 米的园子调的，世界已经是 280×226 米。**

`engine/render/Atmosphere.ts:169` 是 `FogExp2(0.0031)`。指数雾遮蔽率 `1 − exp(−(d·ρ)²)`：

| 距离 | 50 m | 100 m | 200 m | 300 m |
|---|---|---|---|---|
| 遮蔽率 | 2% | 9% | **32%** | **58%** |

老园子最远视距约 80 米，雾只有 6%，等于不存在。现在院墙与山在 200–300 米上，被 32%–58% 的白雾吃掉，
远景糊成一片亮白、地平线发青。参照图的远景也有空气透视，但那是**有颜色的渐变**，我们是一堵白墙。

**判据**：同一条游线上，200 米处的物体仍能分辨轮廓与固有色；远山与天不是同一个白。

**②′ 景深的距离（2026-09-11 追加，修完雾才露出来）。**
`PostFX.ts` 的 `dofFar: 58` 同样是按 64×72 m 园子调的——那时园墙就在 58 m 外，
意思是"最远一线发虚"。切到 280×226 m 后 `smoothstep(26, 58, d)` 让**整个远景满档虚化**，
12 个采样点的螺旋核散成一片，亮处因 luma 加权糊出色边。**已改 220 m**（`89fd8139`）。
**这是第三处同病，判别标准见 `docs/PITFALLS.md` P-17。**

**② AO 半径 0.42 米——那是细节 AO，没有空间 AO。**

`engine/core/PostFX.ts:445` 的 GTAO `radius: 0.42`。这个尺度能压暗石缝、叶根，
**压不暗一个三米高的廊下空间**。参照图的廊靠"越往里越暗"读出进深，柱脚、台阶根、石底都有一圈接触暗；
我们的廊顶是一块从近到远同一亮度的灰板，所以读不出体积。不是算法问题，是只有一档 AO。

**判据**：廊下截图，檐口内侧到廊子深处有可见的亮度梯度；柱础与地面交界处有接触暗。

**③ 廊下那条蓝色地板——很可能是水漫上来了。**

`engine/render/Water.ts:432` 的水是**一整块覆盖全窗口的平面**，靠烘焙的 seabed 图决定哪儿露地
（`makeWaterWindow` 的 `cell = 0.5`）。潇湘馆那条「穿院引泉沟」（`plan.water`，depth 0.3，
原文「開溝僅尺許，灌入牆內，繞階緣屋至前院」）正从院里穿过，而 P1 实测**正房锚点 6 米见方高差 1.30 米**
——地被切下去，水就漫上来。右侧那条沙色生坑是它的另一半。这与 `missing` 的 `99-24` 同源。

**先由 P1 Task 6 收工时复核**；若那时已消失，本条作废，PQ 不必管。

|---|---|---|---|

当时的解法就是用 emissive 假装透光），已有的 bloom 会自然晕开。

**判据**：同机位棚拍与参照图并排；廊的交接处不再有"柱子直接插进平板"的地方；
加这四件后全场景 draw call 增量 ≤ 15，三角数增量 ≤ 8%。

### PQ-7 正门要像门，匾额要挂对（2026-09-11 用户实地走完提出）

#### 一、正门现在是"一间加了门的厅堂"

`builder/parts/damu/building.ts` 的 `menSpec()` 写着 `hall: '厅堂'`，
只把前后檐换成 `front: 'door'` / `back: 'door'`。**所以它读成房间不是错觉。**

真正让一座建筑读成"门"的几件，一件都没有：

| 件 | 原文依据（07-01，已核验通过） | 成本 |
|---|---|---|
| **抱鼓石 / 门枕石** | — | 低。**"门"最强的符号**，比什么都管用 |
| **中柱造 + 板门** | 门装在中柱缝上而非檐柱缝上——有进深、有门洞 | 中 |

已经做对的两条别改回去：「**並無朱粉塗飾**」（素木，不上朱红）、「一色水磨群牆」。

**一条禁令**（07-01 乙方核验注）：园门五间**比荣国府正门三间还高**，是小说给省亲别墅的礼制越格，

#### 二、匾额：两处与我们自己的知识库相反

第十八回同一句话里赐的名（07-37 已录）：
「『大觀園』園之名，『**有鳳來儀**』**賜名曰**『**瀟湘館**』……『蘅芷清芬』**賜名曰**『蘅蕪苑』」。

| 位置 | `plan.json` 现在 | 应为 |
|---|---|---|
| `xiaoxiangguan` 正房 | 匾「有凤来仪」 | **移除**（被赐名替换掉的拟稿） |
| `xiaoxiangguan` 粉垣月洞门 | `plaque: null` | **「潇湘馆」** |
| `zhengmen` 正门 | `plaque: null`（文字曾写死在 `menSpec` 里） | **「大观园」** |

**正房檐下留空。** 第十七回宝玉拟的联「寶鼎茶閒煙尚綠，幽窗棋罷指猶涼」

真要挂是艺术选择，必须进 `provenance.art`，不能当原文依据。

**「大观园」挂正门是艺术摆放**：第十八回元春「因題其園之總名曰『大觀園』」只说了总名，
**没说这块匾挂哪儿**；第五十三回「大觀園正門上也挑著大明角燈」只证明有正门这个地方。
所以挂在正门是我们的选择，不是原文依据——一旦匾额接进 `provenance`，这一条要进 `art` 支。

#### 三、灯有原文依据了

## PE. 园林体验层(把"移步换景"编译出来)

### PE-1 造景关系的数据契约

`plan.json` 与 `scenes/<region>.json` 各加一个 `experience` 段:

```json
{
  "id": "X-01",
  "type": "occlusion",
  "subject": "cuizhang",
  "targets": ["qinfang_ting_qiao", "xiaoxiangguan"],
  "from": [[55, 250]],
  "until": "route:mound_west",
  "source": { "chapter": 17, "quote": "非胸中大有丘壑,焉能想到这里" },
  "assert": "ray",
  "status": "ok"
}
```

`status` 与规则表同口径。`assert` 指明用哪种验法,由 PE-2 的门实现。

### PE-2 体验门 `tools/check-experience.mjs`

### PE-3 从原文抽造景关系

十七回那条游线本身就是一份造景说明书:"一带翠嶂挡在前面""往前一望,见白石崚嶒""
忽闻水声潺潺,泻出石洞""转过山怀,隐隐露出一带黄泥筑就矮墙"。
**叙事就是测量仪器**——原文对"人怎么走、先看见什么"的记录,比对"房子几丈宽"的记录多得多。

## WG. 渲染层迁移到 WebGPU + TSL(2026-09-11 由 codex 方案引入)

方案全文:[`docs/reviews/2026-09-11-webgpu-migration-plan.md`](reviews/2026-09-11-webgpu-migration-plan.md)。
分 WG0 冻结基线 → WG1 棚拍端最小链 → WG2 六组 shader 接通整园 → WG3 恢复后期与质量档 →
WG4 实景验收切默认 → WG5(可选)WebGPU 特有优化。

**核过的事实**(2026-09-11,对本机 three 0.185.1 源码逐条核):

- `three` 0.185.1,`./webgpu` 与 `./tsl` 两个导出入口都在。
- 新 `Info` 里 `render.calls` 与 `render.drawCalls` **是两个不同字段**——
  `tools/capture.mjs:263` 现在取的是 `info.render.calls`,照抄过去口径就变了。
- `ShadowNode.js` 里 VSM 与 `onBeforeShadow`/`onAfterShadow` 都在(33 处命中),
  所以不必为迁移换阴影算法。
- `Frustum.setFromProjectionMatrix(m, coordinateSystem = WebGLCoordinateSystem, reversedDepth = false)`
  ——`engine/scatter/instancing.ts:290` 现在只传第一个参数,在 WebGPU backend 下会**静默剔错**。
- 七个自定义 shader 注入点确实在:`engine/core/PostFX.ts`、`engine/render/Clouds.ts`、
  `engine/render/SkyShader.ts`、`engine/render/Water.ts`、`builder/compose/terrain.ts`、
  `builder/parts/zhiwu/foliage-materials.ts`、`builder/parts/zhiwu/bamboo.ts`。

**它买的是什么,不买什么**:买的是渲染层的余量与 WG5 的 compute 可能性。
**不买帧率承诺**(方案自己声明没跑过性能测试),也**不解决我们当前的痛**——
P1 实测的 28 秒世界构建是 CPU 侧解析场求值,与渲染器无关,方案第 9 行明说了这一点。

**为什么排在 P2 之后而不是紧接 P1**:迁移成功了玩家一个像素都看不出来,做砸了满屏是黑的。
先让园子值得一看,再换发动机。P2/P4/PE 的数据与几何工作与它不冲突(方案第 124 行同此),
但**碰 `terrain.ts` / `vegetation.ts` / `PostFX.ts` 的改动必须排单一窗口**。

**对 P1 单子 F 的即时影响**:F 原计划把 shader 注入做成有序 stage(`rtc` → `wind` → `lod`)。
既然路线已定 TSL,**别再为 GLSL 字符串注入盖一套框架**——那套东西迁移时整个作废。
F 保留分块、分簇、空间索引与构建性能那几项,stage 排序留给 WG2 用节点组合表达。

## PX. 天光与体积云(无依赖,随时可插)

项目最初被 tellux 吸引,就是因为它的云和阳光好看。**观感目标成立,路子不能照抄**:
`@takram/three-atmosphere` 与 `@takram/three-clouds` 按地球尺度设计(球体、ECEF、太空视角),
我们是园林尺度,天空穹顶加 FogExp2 才是对的。见 `docs/tellux-borrowing.md` §8 两个"不要"。

园林尺度自己写够得着的:

- **体积云**:局部天气图 + 两张 3D 噪声(shape / shapeDetail)+ 蓝噪声抖动 + 一到两级云影投到地面。
  不需要地球大气的预计算 LUT。参考 tellux 只做参数映射那一层的做法。
- **阳光**:现在是一盏 key 加天光 hemisphere 加暗暖 bounce(`engine/render/Atmosphere.ts`)。
  要更好看,加的是空气透视(按距离往远处叠天空色)与云影,不是换光照模型。
- **不做昼夜**(2026-09-10 定)。只做白天,时刻固定在艺术圣经 §1 的晴天上午(太阳高度角约 38°)。
  要的是**光影变化**不是时间流逝:云影缓慢掠过地面、树影随风轻晃、水面反光随视角走、
  远景随距离叠天空色。这些都不需要时间轴,也就不需要单一时间源那套基建。
  tellux 调研建议先建 Clock,不采纳,理由见 `docs/tellux-borrowing.md` 的使用说明。

**它不在关键路径上**:纯观感增益,不解锁任何别的东西,与 P1/P2/P3/P4 都没有依赖关系。
分区建设卡在几何与构件上,不卡在天上。想什么时候看见好看的天,就什么时候插进来。
