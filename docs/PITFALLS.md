## P-22 三次连拍的「噪声」没有复现——82k 那次大概率不是读数抖动

**背景**：标准动作第 8 条记着「同一份代码两次量 `mound_block` 差过 82k（2%）」，
但一直没人查过是三角数本身在跳、还是别的什么在跳。单子 AK 建 `perf-baseline.json`
要三次连拍取中位数，顺手把这件事量清楚了。

**量法**：同一份代码（同一次 `vite dev`、未改任何源文件），对四镜各连续跑三次
`tools/capture.mjs`（每次都是独立进程：重新起 chromium、重新建世界、重新读
`window.__GAME__.engine.renderer.info`），逐镜比 `drawCalls` / `triangles` /
`sceneSubmissions`（主场景+阴影提交）/ `frameSubmissions`（整帧提交，含 postfx）。

**结果**：**四镜的这四个数字三次全部逐位相同**，一位不差：

```
gate_approach  drawCalls=269 triangles=4208871  sceneSubmissions{calls:252,triangles:4208854}  frameSubmissions{calls:269,triangles:4208871}
mound_block    drawCalls=255 triangles=4191277  sceneSubmissions{calls:238,triangles:4191260}  frameSubmissions{calls:255,triangles:4191277}
grass_close    drawCalls=292 triangles=4344847  sceneSubmissions{calls:275,triangles:4344830}  frameSubmissions{calls:292,triangles:4344847}
xiaoxiang      drawCalls=250 triangles=3250633  sceneSubmissions{calls:233,triangles:3250616}  frameSubmissions{calls:250,triangles:3250633}
```

只有 `fps` 在跳（`gate_approach` 34/36/38，`grass_close` 47/46/46）——这是已知的、
D-25 明确不比的那部分。

**结论（照实写，不编原因）**：**这次没有复现 82k 的噪声**。三角数与 draw call
在「同一份代码、独立进程连拍」这个条件下是确定性的，说明它不是逐帧簇剔除
相位或阴影级联抖动那类运行时随机性（如果是，同一份代码三次独立建世界不可能
逐位相同）。82k 那次更可能是**两次读数之间代码或状态本身就不同**——例如
中间有源文件改动导致 Vite HMR 触发了部分模块重建、或者两次量隔着不同的
git 提交——而不是同一份代码本身的抖动。**这只是本单三次样本的观察，不是
「噪声不存在」的证明**：真要排除运行时随机性，需要在明确不改任何源文件、
不触发任何 HMR 的前提下再多测几轮，本单没有做那件事。

**留给后面**：如果哪天真的在「确认代码没变」的前提下复现了跳动，先比
`sceneSubmissions` 与 `frameSubmissions` 是否一起跳——一起跳说明是场景图
本身的构件数在变（该去查是不是有条件分支在跑），只有 `frameSubmissions`
跳而 `sceneSubmissions` 不跳，说明是 postfx 那层（例如 SMAA history 相关的
额外 pass）在变。

## P-21 worktree 隔离之后忘了合回来,活悬在 /private/tmp 里

**症状**:2026-09-14 派出三张并行单子,三十分钟后复查,`git log` 上只有两张的提交,
第三张(单子 AI,四件)**一个提交都没有**,工作区也干净——读起来像"这个 agent 挂了或没派出去"。

**真相**:它全做完了。四个提交在 `/private/tmp/dgy-ai` 的**游离 HEAD** 上,
从派单那个 commit 分叉,**从来没合回 `editor`**。`git worktree list` 一眼就看得见:

```
/Users/huanghaibin/Workspace/games   5b6c6575 [editor]
/private/tmp/dgy-ai                  1301bb92 (detached HEAD)   ← 四件活在这里
```

**为什么会这样**:标准动作写的是「分支 `editor`」,而 `feedback` 里另有一条
「要隔离就 `git worktree add --detach`」(那条是为了替换掉更糟的 `git stash`)。
两条加起来,**agent 合理地选了 worktree,但没有任何一条说"收工要合回来"**。

**为什么没被早点发现**:同一轮里单子 V 也用了 worktree(`/private/tmp/dgy-v`),
但它合回来了,所以这个口子一直没露出来。

**代价**:`/private/tmp` 是临时目录,**系统清理会真的删掉它**。
要不是去翻 `worktree list`,这四件活会连同它的推理过程一起消失。

**修法**:标准动作补一条——**要隔离可以用 worktree,但收工必须合回 `editor`,
并在回报里给出合并后的 commit**。见 `docs/superpowers/plans/STANDARD-ACTIONS.md` 第 2 条。

**一条推论**:「做完了」与「交付了」是两件事,worktree 把它们分开了。
以后凡是"某个 agent 零产出"的判断,**先 `git worktree list` 再下结论**。

## P-20 按大尺度对象标定的米制常数,照搬到同一场里的小尺度对象上

**症状**:潇湘馆院内一条「開溝僅尺許」的引泉沟,渲出来是一条**四米多宽的沙疤**,
横穿整个院子。`docs/ROADMAP.md` §PQ-3 的原话:「读感是**地形坏了**,不是没做完——
这是整张图里最像 bug 的一处。」看上去像"缺一圈石压边",其实不是。

**根因**:`builder/compose/terrain-from-plan.ts` 的浅滩沙带用的是**固定米制常数**:

```js
// 水线一圈浅滩沙。园子里没有海滩,这只是池岸的湿脚。
const band = smoothstep(2.0, 0.2, sd) * smoothstep(-2.8, -0.6, sd);
```

注释自己写明它是按**池岸**标定的。可它对 `plan.water[]` 里**每一个**水体都生效,
而那张表里既有 72 m 宽的南池,也有 **0.80 m 宽的引泉沟**:

```
0.8 m 的沟 + 两侧各 2.0 m 沙 = 4.8 m 宽的沙带
```

**同一个教训在同一个文件里已经学过一次**,就在往上 40 行:

```js
// warp 振幅随水面宽度收放：尺许宽的引泉沟经不起米级的扭动。
warpA: Math.min(1.1, inradius * 0.2),
warpB: Math.min(0.35, inradius * 0.06),
```

**`warp` 按 `inradius` 收放了,`sand` 与同一趟算的 `wetBand`(±1.2 m)没有。**

**修法**:凡是"绕着某个对象铺一圈"的米制常数,都要按那个对象自己的尺度收放
(`inradius` 已经在 `Water` 里算好了)。

**与 `P-17` 的区别**:`P-17` 是**世界**变大了、一组参数没跟着重标定,一次性的;
这一条是**同一个场里对象之间差两个数量级**,常数对大的对是的、对小的就错——
**它不会因为重标定一次而消失,只会在下一个小对象上再犯**。

**一条推论**:遇到"这里看着像地形坏了"的时候,先问**这个效果的作用半径是按谁标的**,
再去想要不要加构件。**加构件常常是给错误的宽度描边**——`ROADMAP §PQ-3` 自己警告过
「真正的风险不在构件,在对齐……两者必须由同一份数据生成」,但没看出宽度本身就是错的。

**已修于单子 AH**(2026-09-14):`sand`/`wetBand` 六个常数照 `warpA`/`warpB` 的
`Math.min(cap, inradius * k)` 模式收放,南池等大水体 `inradius` 远超阈值,六个
常数都精确顶到与改动前相同的 cap,池岸沙带逐比特不变。石压边构件
(`builder/parts/pudi/shiyabian.ts`)按 `plan.water[].id` 精确点名,不按
"带不带 `centerline`"过滤——那是流动水系的通用字段,沁芳溪三段与舡坞支港也带,
第一版拿它当过滤条件误把宽水系一并套上了石边,回报里已记这条弯路。

## P-19 并行时 `git add -A` 会把别人的半成品卷进自己的提交

**症状**:单子 O 的提交 `a21e8a6e` 里躺着单子 Q 的三个文件
(`builder/parts/materials.ts`、`builder/parts/qiangyuan/wall.ts`、`builder/parts/qiangyuan/wall-style.ts`)。代码没错、门全绿,
**错的是署名与可回溯性**——将来查"虎皮石是谁做的、为什么这么做",
会查到一条标题讲植物的提交。

**根因**:多个 agent 共用一个工作区时,`git add -A` / `git add .` 的语义是
"把工作区现在的样子都收进来",而工作区现在的样子里有别人正在写的东西。

**修法**:提交一律 `git add <明确路径>`,并在 `git commit` 前
`git status --short` 看一眼暂存区里有没有不属于自己的文件。
已写进 `docs/superpowers/plans/` 各份计划的全局约束。

**同族的三条**(都是"共用一个工作区"这件事的不同侧面):
- P-16/D-20 合并多来源字典时的**静默覆盖**;
- 2026-09-10 单子 A 拿旧副本整份写回,把单子 B 的分派**挤没了**(`3f8088b9` 修);
- 本条:**提交越界**。

**教训**:并行不是"各改各的文件"就够了,**"各提交各的文件"是另一条独立的纪律**。

## P-18 取"下一个编号"用了 tail,撞进已有的号里

**症状**:往 `knowledge/docs/qingshi/07-honglou.md` 追加两条研究,取号 `07-71`、`07-72`
——两个都已经被占了(红香圃、凸碧山庄)。md 里出现同号的两个小节,
`check:rules` 只报出其中一条「状态不符」,**撞号本身它查不出来**。

**根因**:我用 `grep -oE "^### 07-[0-9]+" ... | tail -3` 取最大号。
但这份研究稿**按「通过 / 存疑 / 已否决」分节组织,不是按号排序**,
`tail` 取到的是最后一节的末尾(07-70),不是全文最大号(07-74)。

**修法**:取号一律 `sort -u | sort -t- -k2 -n | tail -1`,或者干脆
`node -e` 读 json 求 max。**并且新条目要同时进 md 与 `*.rules.json`**——
只写 md 会让门报「多 N 条」,只写 json 会让 md 失去出处。

**为什么门没拦住**:一致性门比的是「md 的 id 集合 vs json 的 id 集合」,
同号在集合里会塌成一个,所以**重复不可见**。已知的缺口,记在这里;
真要拦得加一条「md 内同号重复」的检查。

**代价**:发现时另一个 agent 已经把 `07-72` 写进了十来处代码注释,
只能等它提交后统一改。**撞号的修复成本随时间线性增长。**

## P-17 世界尺度变了,所有"米制的观感参数"都要重标定

**症状**:园子从 64×72 m 切到 280×226 m 之后,远景先是糊成一片亮白(雾),修完雾又变成
"模糊得很诡异、很散、还有奇怪的色边"(景深),廊下读不出进深(AO)。三处症状看着毫不相干。

**根因**:同一件事——**三个以米为单位的参数都是按老园子调的,没跟着世界变大**。

| 参数 | 老值 | 老园子里的含义 | 新园子里变成 |
|---|---|---|---|
| `FogExp2` 密度 0.0031 | 最远 80 m 遮 6%,等于不存在 | "几乎没有雾" | 200 m 遮 32%、300 m 遮 58%,**远景变白墙** |
| GTAO `radius` 0.42 m | 压暗石缝、叶根 | "细节 AO" | 压不暗三米高的廊,**廊顶一块平灰板** |
| `dofFar` 58 m | 园墙就在 58 m 外,只有最远一线发虚 | "边缘柔化" | **整个远景满档虚化**,12 个采样点散成一片,亮处 luma 加权糊出色边 |

**修法**:三处都按新视距重标定(0.0017 / 2.4 m / 220 m),并把理由连同老值一起写进注释。

**判别标准**:分清两类米制参数,只有第一类要改。

- **世界的绝对尺度**(雾密度、AO 半径、DOF 距离、地形格边、散布盒)——**必须跟着改**。
- **相对观察者的距离**(`VEG.cullRadius` 41 m、`drawDist` 里的 26/16/27/23、
  `RollingShadow` 的 `halfExtent` 32)——**不用改**。一丛草在 26 m 外就是亚像素,
  跟园子多大无关。

**教训**:**一个参数改坏了另一个参数的症状。** 雾把景深的毛病遮了整整一期——
PQ-0 把雾修对之后,景深的散才露出来。所以世界尺度这种全局改动落地后,
**要把同一量纲的参数一次性全扫一遍**,不要等症状一个一个冒出来。

## P-01 碰撞层的旋转约定与 three 相反

**症状**：桥面能站人，但走到某几段就被一堵看不见的墙挡住；桥栏的碰撞体出现在桥的另一侧。

**根因**：真新镇的 `Collision` 把 box 转到局部坐标时用的是 `Math.cos(-rot)`，与 `THREE.Object3D.rotation.y` 的约定正好相反。原版整个项目所有碰撞体 `rot` 都是 0，这个 bug 从来没暴露过。我们一放旋转的构件就炸了。

**修法**：`engine/player/Collision.ts` 的正变换与逆变换统一成 `world = (lx·cos + lz·sin, −lx·sin + lz·cos)`，与 three 一致。

**教训**：继承来的代码里"从没被用过的参数"是重灾区。给它传第一个非零值时，先单独验一遍。

## P-14 "来源"与"消费"混成一个轴，整章规则被塞错参数集

**症状**：规则一致性门六行全绿，但清官式的走兽、正吻、琉璃瓦等级躺在"江南"参数集里。
Tier A 的正门要用正吻时，得伸手到江南那套里去拿。

**根因**：分派任务时按章节范围划文件——`qingshi/01-04` 给 `qing.rules.json`，
`05-06` 给 `fayuan.rules.json`。但 06 章屋顶瓦作是**官式与苏式两套并存**的，
整章塞进任何一个参数集都是错的。文件名表示"出自哪一章"，参数集表示"哪条链消费"，
这是两个不平行的轴，被我混成了一个。

门查不出来，因为门只按文件对章节，语义错位对它不可见。

06 章逐条判归属：9 条判给 `qing`，2 条 `both`，其余 `fayuan`。

**教训**：数据的组织方式有多个轴时，先问清"这个轴是给谁看的"。

## P-02 构件登记的 glob 落空是静默失败

**症状**：搬家后园子里建筑、墙、石头、桥全没了，只剩地形和植被。编译零报错，测试全过。

**怎么发现的**：不是靠编译，也不是靠逐像素，是靠 draw calls 从 180 掉到 80。见 P-03。

## P-03 逐像素比较在动画场景里没有判别力

**症状**：想用"纯重构应逐像素不变"当回归门，结果同一份构建连拍两次就差 97% 的像素。

**根因**：水面、竹叶、云一直在动，截图采到的动画相位每次都不同。实测平均每像素差 7 到 17 个色阶，`treeline` 有 23% 的像素差超过 24 阶。噪声底比任何有意义的阈值都高。

**排除项**：不是相机。截图工具每次 teleport 到写死的坐标与朝向，对照实验里两次之间相机完全没变。

**修法**：改比 `manifest.json` 的 draw calls、三角数、几何数、材质数——这四项是场景图的函数，确定性的。工具 `tools/manifest-diff.mjs`。观感回归用 `tools/side-by-side.mjs` 出左右对照交人眼。

**根治方案（未做）**：给引擎加冻帧钩子，把动画时钟钉在固定时刻，逐像素就重新可用且锋利得多。

## P-04 材质不缓存实例就合不了 draw call

**症状**：装配器按材质合并静态构件，合完还是几百个 draw call，一点没省。

**根因**：合并是按材质**实例**分桶的。材质库每次 `plasterMaterial()` 都 new 一个新对象，五十个构件就是五十个不同的桶，每桶一个 mesh。

**修法**：材质库加 `memo(key, make)` 实例缓存，同一种材质全园只有一个实例。改完 649 个 draw call 降到 276。

**推论**：任何"要被合并的东西"，判等的那个键必须是共享的。

## P-05 窗纸的 transmission 让帧时翻倍

**症状**：加了半透的窗纸之后，帧率掉一半，而三角数几乎没变。

**根因**：`MeshPhysicalMaterial` 一旦设了 `transmission`，three 会为整个场景多跑一遍透射预渲染（`renderTransmissionPass`）。一栋房子的窗纸就把全场景渲两遍。

**修法**：窗纸不用 transmission，改用 `emissive` 假装透光。

**2026-09-11 实际源码复核**：工厂中仍有 transmission=0.35，本次P1环境收尾才将其移除，并在运行时验收中检查。文档写了修法不代表当前代码已经落实。

**推论**：会触发额外场景 pass 的材质能力，代价不能只按使用面积估计；必须检查整个渲染链。

## P-06 合并几何时索引与顶点色必须先对齐

**症状**：`mergeGeometries` 返回 null，控制台报 "All geometries must have compatible attributes"；或者合并成功但某些构件渲染成全黑。

**根因**：两个。一是 `ExtrudeGeometry`、`ShapeGeometry` 产出的是非索引几何，其余大多带索引，混在一桶里合不了。二是材质开了 `vertexColors` 而某些几何没有 `color` 属性，WebGL 把缺省属性读成 0，也就是黑。

**修法**：合并前统一 `toNonIndexed()`；材质开了 `vertexColors` 的，给没有 `color` 的几何补一份全白。都在 `builder/parts/merge.ts` 里。

## P-07 瓦垄贴图的 UV 周期算错会读成灰板

**症状**：屋面远看是一块均匀的灰，近看才有瓦垄，怎么调法线强度都没用。

**根因**：瓦材质一个贴图周期是 12 垄，UV 缩放要按 `1 / (垄宽 × 12)` 算。当时按 `1 / 垄宽` 算，一个周期被压进一垄的宽度，屏幕上远小于一个像素，直接被 mipmap 平均成灰。

**修法**：`uScale = 1 / (0.2 × 12)`。

**推论**：程序化贴图"看不见细节"时，先算它在屏幕上占几个像素，别急着调强度。

## P-08 木色照色卡填会读成黑

**症状**：按艺术圣经的栗壳色 `#5a3a2a` 填木作，园子里的柱子和梁枋全是黑的。

**根因**：色卡是"物体在中性光下的颜色"，园子里的光是 38° 高度角的暖阳加天光，加上 ACES 色调映射，暗部被压得更暗。

**修法**：色板里的木色整体提亮一档到 `#8a5a3e`，柱子 `#6e4230`，并在艺术圣经里注明"园中光下要比色卡亮一档"。

**推论**：色板要标明"这是屏幕上应该看到的颜色"还是"这是 albedo"。两者在有色调映射的管线里差得很远。

## P-09 亭子上桥被自己的美人靠堵死

**症状**：键盘试玩走到沁芳亭，进得去出不来。

**根因**：两个叠加。一是美人靠的阻挡体没带旋转（同 P-01 那个约定问题的下游），二是亭子默认三面装美人靠，正好把桥的出口那面封了。

**修法**：阻挡体补 `rot`；亭子加 `railingSides` 选项，桥所在的两面不装；并把亭子朝向与桥轴对齐。

**教训**：这个 bug 静态截图完全看不出来，只有键盘试玩能抓。`tools/playtest.mjs` 那次一口气抓了三个真 bug。

## P-10 viewer 的 subject 解析只取两段

**症状**：棚拍 `wall:lattice:wan` 出来的是默认的冰裂纹，不是万字纹。

**根因**：`viewer.ts` 用 `const [subject, variant] = str.split(':')` 解构，第三段被丢掉。

**修法**：构件的 builder 自己兼容一级别名（`wall:wan` 也认）。2026-09-11已改为找到第一个冒号，余下字符串完整交给构件工厂；不能用JavaScript的 `split(':', 2)`，它仍会丢掉第三段。未知建筑预设也不再静默回退。

## P-11 端口被别的项目占用会静默用了别人的服务

**症状**：起了 preview，截图截出来是另一个完全不相干的网站。

**根因**：`vite preview` 默认端口被占时会自动换一个端口，只在日志里说一句 "Port 4173 is in use, trying another one"。而截图工具还在按原端口访问，访问到的是占着那个端口的别人。

**修法**：所有 preview 一律带 `--strictPort`，占用就报错退出。

## P-12 Playwright 截不了正在建世界的页面

**症状**：`page.screenshot()` 超时，日志停在 "fonts loaded"。

**根因**：世界构建是二十秒的同步 CPU 活，占死主线程，截图请求排不上队。加 `animations: 'disabled'` 也没用，那治的是另一个问题（无限 CSS 动画）。

**修法**：要评审载入页 UI，就把 CSS 与 DOM 结构单独渲染到空白页（`tools/loadshot.mjs`），不去截真页面。要截真场景，用 `tools/capture.mjs`，它等的是 `window.__GAME__` 就绪而不是页面静止。

## P-13 `git mv` 多个源到不存在的目录会中断整条链

**症状**：搬家脚本跑完，一半文件搬了一半没搬，`git rm` 那步也没执行。

**根因**：`mkdir -p` 那行漏建了 `knowledge/docs`，`git mv ... knowledge/docs/` 报 "destination is not a directory" 并返回非零，`&&` 链从那里断掉。

**修法**：搬家脚本先建全部目标目录再动手；或者每步单独执行不用 `&&` 串。

**教训**：长 `&&` 链的失败点很难从最终状态反推。宁可分段跑。

## P-15 Node 的 strip-only 模式不支持 TypeScript 参数属性

**症状**：`npm test` 里某个新模块整体挂掉，报 `ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX: TypeScript parameter property is not supported in strip-only mode`。`tsc --noEmit` 完全不报。

**根因**：`constructor(readonly ruleId: string)` 这种参数属性需要真编译才能生成字段赋值，只剥类型做不到。测试跑的是 `node --experimental-strip-types`，编辑器和 `tsc` 跑的是完整 TypeScript，两边对同一份代码的意见不同。

**修法**：字段显式声明 + 构造函数里赋值。`enum`、`namespace`、装饰器同理，都别用。

**推论**：`npm run check` 过了不等于 `npm test` 能跑起来。新建模块后先跑一次测试，别攒到最后。

## P-16 规则号只在规则集内唯一，跨文件有 115 个重号

**症状**：（在加载器落地时当场发现，尚未酿成线上问题）`fashi` 参数集里 `use('06-01')` 拿到的是 **fayuan 的**「清式屋顶形制等级序列」——一条已被驳倒的规则——而不是 fashi 的「界深与提栈起算」。后者状态是通过。

**根因**：六份规则表各自从 `01-01` 编起，273 个 id 里 115 个跨文件重号。加载器把四份表合进一个 `Map<id, Rule>`，后加载的静默覆盖先加载的。而 `fayuan` 有几条标了 `paramSet: "both"`，于是它们跟着进了 fashi 参数集。

两个轴又一次打架：**编号是按来源文件编的，取数是按参数集取的**（同 P-14 的病根）。

**修法**：加载时给每条规则打上来源 `set`；同一 id 在同一参数集里来自多个集时不覆盖，记成歧义，`use()` 遇到就抛并列出限定形式。要用就写 `use('fashi:06-01')`。`RuleBook.collisions()` 列出本参数集的全部重号。

**没做的**：给规则表做全局唯一编号。那要改 388 条数据加六份研究稿的标题，收益只是省掉几个冒号。

**教训**：合并多个来源的字典前，先问"键在合并后还唯一吗"。不唯一时静默覆盖是最坏的行为——它既不报错，又让结果依赖加载顺序。
