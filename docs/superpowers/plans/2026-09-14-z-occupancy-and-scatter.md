# 单子 Z · 占位真源与选料规则 实施计划

**Goal:** 接缝 ③ 占位只有一份真源（销 `missing` 99-25）；接缝 ② 新做一个构件不逐区手写就有区吃到。

**Spec:** `docs/superpowers/specs/2026-09-14-scale-architecture-design.md`（§2 接缝 ② ③、§3 单子 Z）

## Global Constraints

- **不做通用约束求解器**（spec §4、`D-18`「别让 compiler 吞掉大观园」）。
  规则层只有两种谓词：`style` 五维区间、`tier` 白名单。没有布尔组合、没有优先级、没有回溯。
- **不要靠调换建筑与植被的顺序来修 99-25**（`world.ts` 的原警告）。
  那会让手抄的那份变成唯一真源。正解是把占位从「建出来的几何」里解耦成预计算。
- **手写的落位不许被代码偷偷挪走**。散布器读占位场，`placements[]` 只报不改。
- 规则**住在 `builder/` 里，不认识大观园**：说的是「装饰度够的院子檐下挂灯」，
  不是「潇湘馆挂灯」。

## Task 1 · 占位预计算（接缝 ③，销 99-25）

`builder/compose/occupancy.ts`：从 `plan.json` 的 `construction.spec` 编译**檐口外包络**
（`constructionFootprints` 的 `roof`，已含出檐、铺作出跳、生出），加上
`scenes/<region>.json` 的 `clearances[]`。`world.ts` 在「理地」与「植树」之间插一步「圈地」。
`vegetation.ts` 的手抄 `FOOTPRINTS` 表删除，`outsideBuildings()` 函数名与签名不变
（16 处调用点一个都不用改，换的是真源不是用法）。

**验收（spec §3）**：突变测试——把潇湘馆的房子挪 3 m，占位跟着走，不改任何表。

## Task 2 · 「植树」这一步也要自报

清单从 `composer` 的 `Garden` 组搬进共享的 `builder/compose/roster.ts`。
构建顺序是 开天→理地→引水→**植树**→圈地→起屋叠石，「植树」比 `Garden` 组早，
所以它建出来的东西（按 plan 的 `planting` 条目长出来的花池）以前**整步隐形**。

## Task 3 · 「实体在别处」的显式记账

`scenes` 加 `accountedFor[]`：`{ object, by, basis }`。

## Task 4 · 选料规则层（接缝 ②）

`builder/compose/scatter-rules.ts`：规则表 + 匹配器 + `ruleCoverage()`。
`check:scenes` 打印「每条规则落到哪几个区」——**目标 2 的判据就是这张表能当场列出来**。
消费方两处：檐下灯（跟着建筑）、地面散置（跟着地表与占位）。

## 跑出来的结果（2026-09-14，全是实际读数）

### 对账覆盖率一路走到 17/23

| 时点 | 覆盖率 | 野生件 | 发生了什么 |
|---|---|---|---|
| AD 首测 | 10/23 | 44 | 门第一次能看见世界 |
| Y 之后 | 12/23 | 44 | 规则 2 自己把滴翠亭与潇湘馆后房建出来了 |
| **Z 之后** | **17/23** | **40** | 见下 |

Z 这一步的 +5 分成三笔，每一笔的性质都不同：

1. **+2：花池一直长在那儿，只是门看不见。**
   `xiaoxiangguan.path-bed-west/east` 被对账门报了三轮「数据说有、世界没有」，
   查下来 `bedsFromPlan()` 早就在按 plan 长它们——**是整个「植树」这一步一件都不登记**。
   这是 spec §1.5 ②「世界自报的清单是残缺的」在另一层复发：门只看得见登记进来的
   东西，一整个构建步骤不登记，它就整步隐形。
   （顺带：backlog `D1 · PQ-4 花池`「铺装的院子里永远不长花」是**过期条目**，
   `bedsFromPlan` 里写着「花池不问地表是不是草——这是它与自然散布的唯一区别」。）

2. **+3：三条 plan 条目的实体本来就在别处，但要写出来才算数。**
   plan 的 `rocks[]` 里有一半根本不是要摆的石头：

   | 条目 | plan 给的名字 | 实体是什么 | 怎么复验的 |
   |---|---|---|---|
   | `zhengmen.rock-01` | 虎皮石墙基 | 墙构件自带的基座 | 棚拍三种墙，墙脚都有虎皮石 |
   | `cuizhang.rock-03` | 西山口·羊肠小径 | `cuizhang.creek-crossing` 石栈桥 | 锚点 (-37,202) 与 playtest 航点「翠嶂西口石栈桥中」同坐标，该点标高 −1.00 m（溪床） |
   | `xiaoxiangguan.rock-01` | 石子漫成甬路 | `plan.paths` 的铺装 | 沿 x=−105 从 z=104 采到 118，地表逐点都是 `stone` |

   拿太湖石把它们「摆出来」是**伪造覆盖率**——地上会多出三块本不该有的石头。
   但也不能静默豁免。所以做成 `accountedFor[]`：写明 `by`（实体是什么）与
   `basis`（凭什么这么认，尽量是能复验的观测），对账门**单列一栏打印，永远看得见**。

3. **−4 野生件：四盏灯笼改由规则生成**，有出处了（出处是规则与它的 `basis`）。

### 剩下的 6 个缺项，每一个都是真的

`zhengmen.forecourt-terrace`（台矶）、`zhengmen.flanking-wall`（粉墙）、
`qinfang_ting_qiao.pool-railing`（池栏）、`cuizhang.rock-04`（东山脚）、
`qinfang_ting_qiao.rock-01`（石磴穿云）、`cuizhang.rock-02`（镜面白石）。

**其中 `cuizhang.rock-02` 带出一条新发现**：它就是用户要补的
07-04「鏡面白石一塊」題「曲徑通幽處」，而**它在 plan 里的锚点 (−34,200) 标高是 −1.00 m
——在溪床里**。建之前要先定它到底该站哪儿，这是数据问题不是几何问题。

### 占位真源：手抄的那份本来就是错的

| | 手抄的 `FOOTPRINTS` | plan 推导的檐口外包络 |
|---|---|---|
| 正门 | h=(7.4, 3.2) | **h=(10.0, 6.1)** |
| 沁芳亭 | h=(1.6, 1.6) | **h=(2.4, 2.4)** |
| 潇湘馆 | h=(6.8, 4.8) | h=(5.6, 4.2) |

前两条**少算了出檐与铺作出跳，树本来可以长进檐下**；第三条相反，多圈了地。
两年来没人能发现，因为两份真源没有任何一道门去比。

突变测试（`tests/occupancy.test.mjs`）两头都验——挪前在内挪后在外、挪前在外挪后在内。
只验一头的话，一个「把所有地都圈住」的退化实现也能过。

### 选料规则：`check:scenes` 现在能回答目标 2 那句话

```
选料规则会落到哪几个区（✓ = 已建成区，现在就吃得到）
  灯笼-檐下     lantern:gong
    14/19 区：zhengmen✓ qinfang_ting_qiao✓ xiaoxiangguan✓ shengqin_biesu yihongyuan …
  散石-墙根     taihu
    13/19 区：cuizhang✓ xiaoxiangguan✓ daoxiangcun hengwuyuan ouxiangxie …
```

**灯笼那条是最好的样本**：改之前 `lanternSpotsFor` 里写死着

```ts
if (p.part === 'building' && p.variant === 'men') …
if (p.variant === 'qinfang_ting_qiao.pavilion') …
if (p.variant === 'xiaoxiangguan.main-house') …
```

——**加一个区，灯就得回来改这一行**，正是 spec §2 ② 要拆掉的东西。
改成按 `ornament` 挑区、按开间数决定挂几盏之后，**单子 Y 刚建出来的潇湘馆后房
自己就有了灯**（名册从 4 盏变 5 盏），没有人为它写过一行。
稻香村（`ornament` 0.05）则不挂——与 17 回「纸窗木榻，富贵气象一洗皆尽」相合。

`style` 五维在 Z 之前**没有任何代码消费**；现在有了。

### 名册三分，别让一个数失去判别力

第一版把规则生成的 17 块散石算进「野生件」，基线当场从 44 跳到 62 就红了。
但它们**有出处**——出处是规则与它的 `basis`。混在一起的后果是：加一条规则就多几十个
「野生件」，基线一涨再涨，最后没人看它。所以改成三分：

```
covered  对得上 plan 对象
byRule   没有 plan 出处，但由某条选料规则生成      ← 不设上限，压它等于压目标 2
feral    既无 plan 出处也无规则，真正说不清为什么   ← 只许降不许升
```

### 一道顺手立起来的门：手写落位与占位场的冲突

`buildOccupancy` 是纯函数（只吃 plan + scenes），所以 `check:scenes` 不用起浏览器
就能把每条 `placements` 算出世界坐标、问它陷没陷进建筑。**它立刻抓到一个**：

```
手写落位与占位场的冲突  1 处
  撞  xiaoxiangguan/taihu:peak4 陷进占位 0.58m（@ -109.4, 101.6，锚 xiaoxiangguan.main-house）
```

截图对上了：一块大太湖石站在潇湘馆台基上、贴着窗。**只报不改**——挪一块石头是
观感决定，不是机器该替人做的。

判据调过一次，理由写在代码里：第一版把 `clearances` 也当占位，于是「潇湘馆院内
（留给点名竹）」把竹丛报成冲突——**那块地存在的理由就是给竹的**，落进去是本意；
墙与建筑在檐口下咬进 0.05 m 是接头不是穿模。所以只拿建筑发问、深度门槛 0.3 m。
这个数是用来分「接头」和「穿模」的，不是用来把门调绿的。
